# ADR 0006: A1 Semantic Matrix and Durable Disagreement Evidence Hard Grill

**Status**: implemented for the bounded seed-2 coordinate  
**Date**: 2026-08-24  
**Pressure**: Hard  
**Scope**: decide whether to move from the bounded Supplier seed-1 capsule directly to fixed-plan
verification, or first close the semantic and evidence defects exposed outside its selected set

## Target

OAC must show that an organizational contract is implementable from public rules by replaceable
semantic kernels. Exact agreement on three frozen reports and six generated variants is useful, but it
is not enough if adjacent valid inputs expose unresolved meaning. The next increment must increase the
falsifiability and replayability of the standard rather than merely increase a passing case count.

This ADR records a self-administered Hard Grill. Each question selects the recommended answer because
the user explicitly authorized self-questioning against the previously aligned OAC objective.

## Question 1: Should implementation proceed directly to stdio-v2 `verify`?

**Options**: A. yes, because the selected 34 observations pass; B. first resolve only the six initially
noticed examples; C. first freeze the semantic branch classes and evidence chain; D. broaden the claim
and defer discrepancies; E. replace exact parity with final-verdict equality.

**Recommended answer**: C.

**Why it matters**: verification built on an ambiguous derivation contract can make two verifiers agree
for opposite or incomplete obligations.

**Observed pressure evidence**: a systematic admission-status and boundary mutation sweep found many
input-level disagreements. They collapse into a smaller set of rule classes, but prove that `34/34`
means only `34/34 selected observations`, not complete Supplier v0.2 support.

## Question 2: Is Python output the normative oracle for resolving those classes?

**Options**: A. always; B. majority vote; C. public rule and safety invariant first, with either or both
implementations allowed to be wrong; D. preserve both outputs as valid; E. choose the shorter output.

**Recommended answer**: C.

**Why it matters**: treating the reference implementation as law would turn the conformance kit into a
compatibility harness and would conceal shared semantic defects.

The sweep already exposed one likely shared defect: a candidate/disputed changed subject is an Unknown
closure root, so a completed report, when one is legal, must set `rootApplicabilityUnknown=true`.

## Question 3: What semantic rules should be frozen before a successor capsule?

**Recommended answer**: freeze the following rules as one reviewed decision set:

1. A retracted changed subject fails before derivation with `RETRACTED_SOURCE_EXCLUDED`; it is not a
   valid active root from which to prove organizational non-impact.
2. Every declared edge, rule, and duty remains visible in the applicability evaluation ledger.
   Retraction evaluates `FALSE/RETRACTED_SOURCE_EXCLUDED`; it prevents path materialization but does not
   erase the historical source from the audit projection.
3. A candidate/disputed applicability source uses the generic atom reason
   `CANDIDATE_INPUT_NOT_AUTHORITY`. Closure over a candidate/disputed dependency edge additionally uses
   `CANDIDATE_EDGE_NOT_AUTHORITY` on the path. Predicate truth and propagation authority are separate.
4. Candidate and disputed changed subjects seed Unknown and make
   `rootApplicabilityUnknown=true`. No rule may upgrade such a subject to Affected authority.
5. Complete-boundary residual results require the full bounded non-impact proof: admitted root,
   admitted TRUE prefix, admitted FALSE cut, no bypass, complete coverage, decisive evaluation refs,
   and no reachable continuation hidden beyond `maxDepth`. Local absence of an Affected path is not a
   proof.
6. Retracted residual nodes emit `out_of_declared_scope/excluded` paths. Candidate/disputed or uncovered
   residual nodes remain Unknown unless the authoritative FALSE-cut proof is present.
7. Legacy discovery fallback is exactly `obligationType=discover_dependency` with
   `requiredEvidence=[dependency_admission_decision]`. A contextual aggregate must use its explicit
   discovery triple.
8. A partial/unknown boundary without explicit `knownGaps` or `discoveryTargetRef` emits the canonical
   target `urn:oac:boundary:unobserved`.
9. `unresolvedRefs` contains Unknown paths, only Unknown evaluations referenced by emitted paths, and
   the change root when root applicability is Unknown. An unrelated Unknown negative control is not an
   unresolved business dependency.
10. An admitted UnknownTransitionDuty whose required role is not admitted fails with
    `UNKNOWN_TRANSITION_DUTY_INVALID` before downstream prerequisite-order errors.

**Why it matters**: these rules explain whole classes of mutation failures and can be implemented and
tested without standardizing one Agent topology.

## Question 4: Should seed-1 be rewritten in place?

**Options**: A. overwrite it and reuse the digest language; B. preserve it as a historical development
coordinate and publish a successor seed; C. delete all prior evidence; D. silently change only docs.

**Recommended answer**: B.

**Why it matters**: a digest-named result is useful only if later corrections do not impersonate the
original run.

Seed-1 is explicitly superseded as claim evidence because its pinned stdio-v2 text advertises a broader
capability than the adapters, its generated-case source was not frozen, and its installed-artifact claim
was not replayed against the final capability tuple. The successor must use a new capsule ID, digest,
generator artifact, capability set, validation report, and installed replay.

## Question 5: What makes generated evidence durable?

**Recommended answer**: separate the generator from the mutable harness and bind all of the following:

- a versioned, content-digested mutation recipe set;
- exact generator source and runtime/dependency ledger;
- raw original and reproducer inputs;
- complete response JCS for both incident implementations;
- command/source/runtime/build digests and capability statements;
- an immutable open incident plus a separate resolution record;
- the exact profile/protocol/capability-set digests that resolved the question.

The harness consumes the pinned recipe artifact; it does not compute `generatorDigest` over its own
ever-changing source. A PASS summary includes both implementation material identities and is stored as
exact JCS, not represented only by a number in Markdown.

## Question 6: How broad should the successor mutation set be?

**Options**: A. only the six old variants; B. every combinatorial mutation immediately; C. one or more
representatives for each normative branch plus metamorphic candidate/disputed and ordering equivalence,
then systematic expansion; D. random fuzzing without a seed ledger; E. frozen reports only.

**Recommended answer**: C.

**Why it matters**: representative semantic coverage is reviewable and falsifiable, while an unbounded
Cartesian product delays the MVP and a tiny hand-picked set invites overfitting.

At minimum the successor derive set covers: retracted root; candidate root without prerequisite noise;
candidate and retracted edge; retracted rule and duty ledger retention; retracted residual node;
candidate residual with and without an authoritative FALSE cut; candidate downstream source; depth-one
and depth-two continuation; implicit partial boundary; legacy discovery fallback; contextual discovery
aggregate; non-admitted duty role; referenced versus unrelated Unknown evaluations; and input set-order
metamorphisms. A canned-three mutant remains only one named mutant, not general anti-cheating evidence.

## Question 7: When may the capability claim be widened?

**Recommended answer**: not in this increment. The successor advertises a new bounded evidence-set
coordinate while reports remain bound to `oac.supplier.transfer/v0.2`. Full Profile capability requires
a separately frozen complete RequirementSet, no open scored disagreements, clean installed replay, and
eventually an independently maintained implementation.

**Why it matters**: capability identity must describe what was tested, not what the implementation hopes
to support.

## Question 8: What is the exit condition for this increment?

**Recommended answer**: exit only when:

1. every identified semantic class has an incident or shared-defect record and a public normative
   resolution;
2. both kernels implement the frozen decisions;
3. all successor frozen/generated observations agree in exact status, reason, and report JCS;
4. the old canned-report mutant and at least one reason/root-forgery mutant are rejected;
5. the summary binds capsule, generator, harness, capability set, implementations, observations, and
   mutants;
6. source, clean build, isolated install, and complete quality gates reproduce the recorded result; and
7. docs state both the achieved bounded evidence and the remaining non-independent/full-profile limits.

## Decision

```text
seed-1 selected parity
        ↓ red-team mutation sweep
semantic rule classes + disagreement records
        ↓ public Profile / protocol / capability-set resolution
seed-2 content-bound generator + branch matrix
        ↓ Python / internal Go exact parity + mutation rejection
durable validation manifest and honest bounded claim
        ↓ only then
stdio-v2 plural fixed-plan verify
```

This decision is deliberately a standardization step, not a new Agent runtime feature. It makes OAC
more useful precisely because implementers can disagree, expose the ambiguity, resolve it in public
contract artifacts, and then converge without sharing an Agent topology or semantic runtime.

## Implementation result

The bounded exit was reached on 2026-08-24: source and isolated-wheel replay each passed 52/52 selected
observations, seven historical disagreements were preserved with separate resolutions, and the
canned-three plus candidate-root-forgery mutants were rejected. Exact coordinates and limitations are
recorded in `docs/validation/STATUS-v0.5-a1-semantic-matrix.md`.

Exit condition 6 is only partially closed: isolated install and byte-reproducible wheel/Go builds pass,
but no clean Git archive exists for this uncommitted source state. That keeps archive tasks open without
invalidating the narrower seed-2 working-tree result.
