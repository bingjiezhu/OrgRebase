# 核心方法：让企业变更有据可查地生效

企业变更包括事实、政策、职责和产品方案等变化。假设一家企业把某类报价的折扣规则从 5% 调到 10%：改一个数字并不难；难的是知道哪些现有报价依赖旧规则、哪些工作可以保留、谁有权决定，以及系统最后交付的结果是否就是被批准的那一版。这里的百分比只是说明问题，不是公开交易数据中的历史政策或客户实测结果。

OrgRebase 将企业变更表示为来源与权限绑定的工作更新。**企业提供事实、规则、责任和目标；Agent、Tool、Skill 准备候选与证据；确定性控制面裁决影响和资格；精确负责人批准；授权执行者应用并留下后继版本与回执。** 当前可运行的参考场景是企业报价，其他业务类型需要单独适配和验收。

## 当前支持的变化范围

| 变化 | 当前实现范围 |
|---|---|
| 上线日期、币种、产品方案 | 报价参考路径按已准入来源和依赖形成候选并执行受治理更新 |
| 商品明细、整单折扣、价外税 | 需要显式采用计价模板 v2 和相应企业包；金额计算不等于已写回客户 CRM |
| Quote 与 Discount Memo 的共同变化 | 仅显式双成果 profile；在新建隔离工作区受控验证，外部效果关闭 |
| 负责人职责移交 | 仅部署方显式启用的双人确认政策；不等于任意委派或自动改变企业身份 |

新业务成果需要自己的 handler、来源绑定、负责人和验收。列表列的是已支持路径，不是对企业全部变更的覆盖承诺。

## 一次企业变更如何走完

1. **先确定依据。** 企业材料经过预检、密封、准入和激活；变化绑定确切来源版本、业务对象和负责人。模型给出的文字不能自行成为企业事实。
2. **只组织必要的工作。** 控制面根据已准入能力、依赖和实际读取记录形成领域任务与受限上下文。任务可以跨轮调整，同一轮中已经准入的计划不就地改写。AgentTeams 记录任务执行与交接，不持有业务批准权。
3. **把候选与影响分开核对。** Agent、Tool、Skill 可以提出候选；控制面独立检查来源、权限、依赖及预演结果。受影响、可在声明边界内保留、以及仍未知的对象必须分开；证据不足时保留 `UNKNOWN`，不能猜成“不受影响”。
4. **批准精确版本，再单独生效。** 负责人审阅自己范围内的确切差异和摘要。批准后业务结果仍未改变；有执行权限的主体才可提交 Apply。控制面在提交时重验版本与权限，只更新获准且确实受影响的对象。
5. **留下可恢复的结果。** 后继 Quote、依赖、差异、批准与应用回执有独立身份。请求失败或结果未知先按同一操作身份对账，不盲目重发；外部系统效果还需单独授权和回查。

## 设计决策与边界

| 设计 | 解决的问题 | 当前边界 |
|---|---|---|
| **组织契约与按需任务** | 把事实、责任、能力和上下文先约束清楚，再安排协作 | OAC 是标准草案；当前报价参考链有受控验证，不是通用企业接入认证 |
| **依赖驱动的选择性 Rebase** | 上游发生变化时，不把所有成果重做，也不把未覆盖的依赖当作安全 | 当前有报价路径与显式 Quote＋Discount Memo 配置；任意新成果仍需 handler、来源与验收 |
| **候选、批准、生效分权** | 避免模型输出或任务完成直接改写正式业务状态 | 人工批准与 Apply 各自绑定精确对象；真实客户身份和权限仍待客户环境验收 |
| **可治理的能力演化** | 从失败和补证中提出有来源的经验/Skill 候选，并允许拒绝、撤回和恢复 | 已有受控切片；跨任务质量证明、正式发布、真实采用和业务收益仍开放 |

这些设计贯穿同一条业务链。当前企业报价负责人是主用户；Product、Legal、Finance 和 GTM 提供领域候选，并由各自的人类负责人持有业务权威。参与领域、模型调用和并发范围取决于准入的任务与执行模式。

## 从哪里验证

先按[快速开始](quickstart.zh.md)用公开历史商品复算一笔报价；商品明细来自公开数据，折扣、税率与身份为受控配置。再用[浏览器演示](demo.zh.md)观察候选、退回补证、批准与应用。架构和各层责任见[权威边界](architecture.zh.md)，企业接入及外部效果条件见[部署与运维](deployment.zh.md)。

`0.5.0b4` Beta 的工程证据上限是**受控本地验证**。真实客户部署、生产容量、跨企业泛化、员工 UAT 和 ROI 都须另行验收；网站或演讲中的示意流程不能代替这些结果。
